# 过滤配置、决策与验证

## 页面入口

- **过滤器**：名称可打开只读详情；可查看全部配置值、当前引用、近 24 小时实时执行次数、版本历史与运行记录。
- **过滤器 → 编辑当前保存版本**：桌面左侧配置、右侧测试；移动端使用“条件配置 / 效果测试”标签。保存共享配置前提示受影响的 Flow 节点和 AI Profile。
- **过滤器 → 修改历史**：可把旧版本载入草稿，与当前保存版本比较；只有明确保存新版本才会生效，不覆盖历史版本。
- **消息中心 → 消息详情 → 处理决策**：查看当时的 Flow、分支、过滤器版本、逐条件判断、命中证据、目标与任务。共享过滤器链接会定位到执行时版本，而不是用当前配置冒充历史配置。
- **消息详情 → 按当前配置重新评估**：只读模拟；当前内容 revision 与历史决策 revision 分开显示。没有历史决策的旧消息显示“未记录”。
- **转发编排 → 选中 Flow → 真实结构 / 预演**：资源概览只是引用关系；真实 DAG 展示串联、分支和汇合，全链路模拟包含同源 Flow 的优先级与命中即停。
- **AI 整理 → 自定义条件 → 仅测试过滤条件**：不会调用模型或投递。原有完整 AI“试运行”仍会调用模型，两者不要混淆。
- **设置 → 消息与投递记录归档 → 过滤决策保留(天)**：默认 30 天；0 表示不自动清理。保存后热生效，也可单独手工清理过期决策。原消息删除仍会级联删除关联决策。

## 判断语义

1. 旧条件数组继续按 AND 执行；新配置可用 `all` / `any` 分组和 `negate`，最多 100 个条件、3 层分组。一个节点或 AI Profile 最多引用 32 个共享过滤器。
2. 一个共享过滤器只包含条件，不是全局黑名单。必须被 Flow 或 AI 整理引用才生效；停用引用方不会删除共享配置。
3. 串联过滤为 AND；并联路径汇合为 OR。一个分支拦截不代表其他分支也被拦截。命中即停仅在某个 Flow 产生目标后阻止后续低优先级 Flow。
4. 单次求值固定共享过滤器快照并批量读取；保存新版本影响后续求值，不会撤销已经生成的任务。
5. 关键词默认只检查正文，保持原有子串和大小写规则。链接地址、附件名称、附件说明、NFKC 和不可见字符处理均需显式选择。不包含 OCR 或语义识别。
6. 时间窗口默认用发送时间，缺失时回退接收时间；可显式改用接收时间。未指定时区的旧配置仍用服务器时区；新建条件默认 Asia/Shanghai。首尾分钟均包含，相同起止时间只匹配该分钟。
7. Telegram 照片为 `photo`，图片文件为 `image`；音视频/语音被正确识别。`image_any` 匹配全部图片；`document` 保持旧“文档及音视频”宽匹配，`file` 才只匹配普通文件。旧文档记录在 MIME 信息足够时可识别音视频，不能从旧 MIME 无依据地推断语音。Source 自定义类型仍按准确字符串匹配。
8. 编辑补发仅向“历史目的地身份（Flow/节点/渠道）与当前匹配结果”的交集补发，使用当前处理快照和当前目标模板；不退回未经处理的原文，不新增历史之外的目的地。保留的 Flow 节点 ID 在保存后保持稳定。
9. 新消息求值、编辑求值、旧任务重试和当前配置重评是不同操作。预演不创建任务、不发送、不调用 AI，也不模拟队列幂等或 Telegram 是否实际发生内容变化。编辑模拟把当前内容视为假设的新版本，只检查过滤和历史路由交集。
10. 配置不存在、读取失败、非法 ID、空发送者限制、错误类型、非法正则等均不静默放行。执行错误不是“正常未匹配”。AI 解析共享过滤器失败会结束本次运行，不能降级为无条件调用模型。

## 决策与投递状态

- 实时任务与决策证据在同一数据库事务内提交，提交后才唤醒 worker；审计写入失败会回滚新任务，并尽可能另记失败决策。
- 数据库未确认事务提交结果时显示“不确定”，不能据此断言任务未入队或已送达。
- 已匹配目标不等于已入队，已入队不等于外部发送成功。任务幂等冲突单独标记“任务已存在（未重复入队）”。
- 条件短路和不可达节点标记“未执行”，不是自动推算其判断结果。过滤器与节点配置版本、内联配置快照和实际路径信息与记录一起保留。
- 明确删除共享过滤器时会连同该过滤器的配置版本历史删除，消息决策中的版本摘要与判断结果仍保留；需要长期完整还原配置时，不要删除该过滤器，或先保留配置备份。
- 配置备份不是运行库全量备份，不包含完整决策和版本历史。同实例恢复会保留已有历史、生成更高的新本地版本，并保留仍存在的 Flow 节点身份；新实例恢复会为当前配置建立 v1 基线。Flow、AI 和嵌套 source 条件中的引用会重新映射，缺失过滤限制会拒绝并回滚恢复，不能静默删除限制。
- 决策详情有 1 MiB 上限，过大时明确标记部分详情被省略，同时保留完整过滤器执行统计与有界的节点摘要；普通日志不输出消息正文和凭证。
- 近 24 小时统计计量的是实时 Flow 中过滤器执行次数，同一消息可能经过多个节点；不是去重消息数，也不包含 AI 运行次数。AI 的纳入/排除与过滤详情在对应 Run 查看。
- 历史试算必须指定来源和不超过 31 天的接收时间范围，每页最多 100 条（界面默认 50）；每页通过/拦截/变化统计只代表本页样本。

## 上线与回滚

1. 先备份数据库；暂停旧服务后执行新增 goose migration `00034_filter_decisions.sql` 与 `00035_filter_reference_indexes.sql`。正式迁移中没有测试 seed，也不使用 GORM AutoMigrate。
2. 34 为现有过滤器建立 v1 基线，新增版本历史、实时决策、AI 条件追踪；35 增加共享引用索引。旧条件数组不会自动转换匹配范围或文本规范化。
3. 构建前端并嵌入后端：`cd web; npm run build:embed`，然后在项目根目录 `go build ./...`。按现有部署方式发布配套前后端。
4. 新保存的配置先用正、反样例和历史样本比较，重点检查编辑补发、并联路径、低优先级兜底和时间窗口。不要用真实生产渠道发送测试消息来代替只读预演。
5. 如果已有配置含分组、取反、扩展范围等新能力，**不能只回滚旧二进制**：旧代码可能忽略新字段或无法执行新条件。应先准备经过验证的旧格式配置快照，再协调回滚。
6. 不要在生产直接 `down` 删除新审计表来回滚业务；它会删除版本和决策历史。优先保留新增表，并恢复备份/兼容配置。数据库回退验证只在独立测试 schema 中执行。
7. 修复后，旧共享 `source` 条件在 AI 整理中也会真实执行；原先靠“被忽略”放行的消息可能不再纳入。非法存量条件和超限配置会明确报错，不会被静默清空或截断。

## 开发验证

```powershell
go test -count=1 ./...
go build ./...
go vet ./...
cd web
npm run test:filters
npm run build
```

前端过滤测试使用 Node 内置 test runner 和 TypeScript strip，需要支持 `--experimental-strip-types` 的 Node（本轮使用 Node 24）。不新增测试框架依赖。

数据库测试不会读取本地生产配置，必须显式设置 `TMF_FILTER_TEST_DSN` 为独立本机 `postgres://` URL，然后执行：

```powershell
go test ./internal/storage/repository -run 'TestFilter(Decision|Backup)DatabaseRoundTrip' -v -count=1 -timeout 120s
```

测试会建立唯一 `tmf_filter_test_*` schema，执行真实 SQL migration，验证版本/引用、AI 条件追踪、消息入库与编辑、任务幂等、事务回滚、过滤统计、只读预演、清理和备份恢复；最后仅删除该测试 schema。`pg_trgm` 扩展会创建在测试数据库的 public schema，因此必须使用专用可丢弃数据库。不要指向生产数据库或生产数据库的本机隧道。本轮 SQL 验证采用 PGlite PostgreSQL WASM 内核，不替代目标 PostgreSQL 版本、并发锁竞争或生产容量验收。

浏览器验收可显式设置 `TMF_FILTER_UI_ADDR=127.0.0.1:4179`、`TMF_FILTER_UI_WEB_DIR` 为 `web/dist` 绝对路径，以及可选的 `TMF_FILTER_UI_STOP_FILE`，再运行：

```powershell
go test ./internal/storage/repository -run TestFilterUIHarness -v -count=1 -timeout 17m
```

该夹具使用真实应用服务和独立 SQL schema，只提供隔离样例，不启动 worker、Telegram 或 AI Provider。创建指定 stop file 可结束；否则最多 15 分钟后停止并清理 schema。它不代表生产 Telegram 或外部 Sink 验收。
